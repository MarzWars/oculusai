OCULUS CHESS — MASTER IMPLEMENTATION PLAN
Version: 1.0
Date: 2026-10-15
Purpose: Build a reliable, visual, interactive chess-playing and coaching module inside the existing Oculus AI application.

======================================================================
0. PROJECT MISSION AND NON-NEGOTIABLE PRINCIPLES
======================================================================

PROJECT GOAL

Build Oculus Chess as a serious chess coach, not merely a chatbot that can talk about chess. It must support legal live chess, PGN game import, game replay, Stockfish-backed analysis, understandable explanations, visual teaching on a live chessboard, interactive exercises, and eventually long-term personalized coaching based on a user's games.

Core product promise:
"Do not merely tell me that a move was bad. Show me what I missed, why it mattered, what I should have considered, what the better plan was, and how I can train to avoid the same mistake."

NON-NEGOTIABLE ARCHITECTURAL RULES

1. A deterministic chess library owns the canonical board state and legal move rules.
2. Stockfish (or another explicitly approved UCI chess engine) performs objective chess calculation and evaluation.
3. Oculus's language model explains, teaches, asks questions, and personalizes lessons. It is not the authority for legality or engine facts.
4. The frontend board is a visualization and interaction surface. The server-side chess state is authoritative.
5. Every user move and AI-suggested move must be validated server-side before it changes the game.
6. Never infer the current position from a long natural-language conversation. Supply the exact current FEN and structured analysis data.
7. Do not invent engine evaluations, principal variations, legal moves, or chess facts. If data is unavailable, state that clearly.
8. Preserve the existing Oculus application, styling, authentication, AI routing, and database architecture where practical. Do not rewrite the application merely to simplify this feature.
9. Build in phases. Test each phase before moving on.
10. Prefer complete, maintainable files over unexplained snippets when making substantial changes. Avoid unnecessary duplication and oversized files.
11. Keep secrets and provider credentials server-side. Validate all user input.
12. Do not claim the system is production-ready until the relevant acceptance criteria and tests pass.

TECHNICAL DEFAULTS

- Preferred chess rules/state library: python-chess, if compatible with the existing backend.
- Preferred engine: Stockfish via the UCI protocol, with a configurable executable path and analysis limits.
- Frontend: use the existing Oculus frontend framework and component conventions. Choose a compatible chessboard library only after auditing the project.
- Backend: use the existing backend framework. If the application is already Python-based, integrate python-chess there. If not, assess whether a small Python chess service is appropriate and document the operational trade-offs before implementing it.
- Database: use the existing database and migration system. Do not introduce a new database without a clear technical reason.
- AI: use Oculus's existing model/provider abstraction, including OpenRouter if that is already the configured route. Do not hardcode one model into the chess subsystem.
- Design: fit Oculus's dark, premium, futuristic interface and existing purple/neon accent system.

Do not assume any file paths, frameworks, environment variables, or database tables before inspecting the repository.

5. PHASE 3 — STOCKFISH INTEGRATION
======================================================================

Goal: add objective engine analysis without allowing the LLM to fabricate results.

Tasks:
3.1 Integrate Stockfish using its supported UCI interface.
3.2 Verify engine installation, executable path, version, license, and deployment requirements.
3.3 Provide configurable analysis time/depth and resource limits.
3.4 Support best move, evaluation, principal variation (PV), depth, nodes when available, and MultiPV.
3.5 Normalize engine output into a stable internal schema.
3.6 Define evaluation perspective explicitly: side to move, White, or another documented convention. Convert consistently.
3.7 Represent mate scores separately from centipawn scores.
3.8 Convert engine moves to SAN only using the matching board position.
3.9 Validate every engine move against the position before exposing or applying it.
3.10 Add timeouts, cancellation, cleanup, and bounded concurrency.
3.11 Cache reusable analysis using a normalized position and relevant engine settings, such as FEN, engine version, depth/time limit, and MultiPV.
3.12 Never run unbounded engine searches from a user request.
3.13 Ensure the engine service can be tested independently from the UI and LLM.

Analysis data should include, where available:
- FEN
- Side to move
- Evaluation
- Evaluation perspective
- Mate score
- Best move in UCI and SAN
- Principal variation in UCI and SAN
- MultiPV candidates
- Search depth
- Search time/nodes
- Engine/version metadata

Acceptance criteria:
- Stockfish can analyze a supplied position and return valid structured data.
- Evaluations have an unambiguous perspective.
- Mate scores are handled correctly.
- Engine failures and timeouts do not corrupt games.
- Concurrent analysis stays within configured limits.

7. PHASE 5 — GAME ANALYSIS PIPELINE
======================================================================

Goal: analyze each move consistently and store the evidence needed for coaching.

Tasks:
5.1 Analyze positions before and after each played move.
5.2 Determine the engine's preferred candidate moves and PVs.
5.3 Evaluate the played move using a documented analysis approach. Avoid comparing scores from incompatible search conditions without acknowledging the limitation.
5.4 Normalize evaluation changes to the player's perspective so positive/negative changes are interpreted consistently.
5.5 Handle mate transitions separately from ordinary centipawn changes.
5.6 Detect candidate critical moments: major evaluation swings, missed tactical chances, forced sequences, opening transitions, and endgame decisions.
5.7 Store analysis status, engine settings, and timestamps.
5.8 Support cancellation, retry, resumable work, and partial analysis.
5.9 Avoid duplicate engine work when analysis already exists at equivalent settings.
5.10 Make analysis depth/time configurable by mode: Fast, Normal, Deep, and Intensive.
5.11 Keep raw engine facts separate from generated explanations.
5.12 Do not imply that shallow analysis is definitive.

Acceptance criteria:
- Every analyzed move has traceable before/after positions and analysis settings.
- Evaluation perspective is consistent.
- Analysis can be resumed after failure.
- Critical-moment selection is deterministic and testable where possible.

8. PHASE 6 — MOVE QUALITY AND MISTAKE CLASSIFICATION
======================================================================

Goal: create a transparent, configurable move-labeling system.

Possible labels:
- Best
- Excellent
- Strong
- Good
- Inaccuracy
- Mistake
- Blunder
- Missed opportunity
- Tactical error
- Strategic/positional error
- Opening error
- Endgame error
- King-safety error
- Calculation error
- Brilliant (only when the evidence supports a defined special criterion)

Important rules:
6.1 Do not claim to reproduce Chess.com's proprietary classifications exactly.
6.2 Document classification thresholds and tune them through tests.
6.3 Do not classify from raw evaluation swing alone.
6.4 Consider position context, forced alternatives, mate, material, whether the position was already lost/won, and whether the move was practically or objectively significant.
6.5 Distinguish objective move quality from pedagogical category. A move can be a mistake and also a strategic error.
6.6 Be conservative with "Brilliant"; require an explicit, testable criterion such as a sound, non-obvious sacrifice or another justified feature. Do not use the label as decoration.
6.7 Permit "uncertain/unclassified" if the analysis is insufficient.
6.8 Store the evidence and rule/version used to assign a label.

Acceptance criteria:
- Classification rules are documented and covered by representative tests.
- Mate-score transitions and already decisive positions are handled sensibly.
- Labels are not presented as more precise than the engine analysis supports.

9. PHASE 7 — POSITION FEATURES AND CHESS MOTIFS
======================================================================

Goal: derive meaningful features that help explain why a move matters.

Tactical concepts to detect where feasible:
- Fork and double attack
- Pin and skewer
- Discovered attack/check
- Deflection and attraction
- Removing a defender
- Zwischenzug
- Back-rank tactic
- Hanging or trapped piece
- Mate threat and forced mate
- Promotion threats
- Sacrifices and tactical exchanges

Strategic concepts to assess where feasible:
- King safety
- Piece activity and coordination
- Weak squares and weak pawns
- Pawn structure and pawn breaks
- Open files and diagonals
- Outposts
- Space and central control
- Good/bad bishops
- Poorly placed pieces
- Passed pawns
- Rook activity
- Prophylaxis and opponent-threat recognition

Endgame concepts to assess where feasible:
- King activity
- Opposition
- Passed-pawn races
- Rook activity
- Zugzwang
- Basic theoretical endings
- Conversion and defensive technique

Implementation rules:
7.1 Do not pretend a motif detector is infallible.
7.2 Use deterministic rules, engine variations, and validated board features where possible.
7.3 Treat LLM-suggested motifs as hypotheses until checked against the position and engine evidence.
7.4 Attach confidence or evidence where practical.
7.5 Prioritize the features required for explanations before attempting exhaustive motif detection.

Acceptance criteria:
- Each generated motif references a real position and relevant pieces/squares/line.
- Unsupported motifs are omitted or marked uncertain.
- Motif detection does not alter the chess state.

11. PHASE 9 — OCULUS EXPLANATION ENGINE
======================================================================

Goal: turn verified chess evidence into accurate, human-level teaching.

Oculus should explain:
1. What the player played.
2. Why it was good, inaccurate, or bad.
3. What the opponent's move changed or threatened.
4. What the player should have considered.
5. The best or most instructive alternative.
6. The likely continuation and its purpose.
7. The chess principle involved.
8. How to recognize the same pattern in future games.

Example of the desired style:
"Your move looks natural because it wins a pawn, but it allows your opponent to activate a piece with tempo and leaves your king-side pieces uncoordinated. The stronger move keeps the centre stable and gives you time to finish development. The issue is not simply that the engine prefers another move; it is that your move ignored the opponent's next threat."

That example is illustrative only. The actual explanation must match the supplied position and engine evidence.

Tasks:
9.1 Define a strict prompt/input schema for coaching events.
9.2 Require the model to distinguish engine facts from interpretation.
9.3 Require SAN/UCI moves in explanations to come from supplied legal lines.
9.4 Ask the model to avoid unsupported claims and say when evidence is insufficient.
9.5 Support explanation depth: Beginner, Club Player, Advanced, Expert.
9.6 Support concise, detailed, strategic, tactical, and Socratic coaching styles.
9.7 Keep the explanation relevant to the actual position, not generic chess advice.
9.8 Avoid overconfident claims about the user's thought process. Say "you may have overlooked..." rather than asserting what the user was thinking.
9.9 Validate any moves returned by the model before rendering them as executable or animatable.
9.10 Keep model output structured enough for the frontend to render text, lines, arrows, highlights, and teaching steps.

Acceptance criteria:
- Explanations cite the actual move and position.
- The model does not invent engine scores or variations.
- Every move used for an animation is validated.
- Explanation output can be rendered in the UI without fragile free-form parsing.

14. PHASE 12 — "PLAY AGAINST YOUR PAST SELF"
======================================================================

Goal: convert mistakes from a user's own games into training positions.

Workflow:
1. Open an analyzed game.
2. Navigate to a critical position before the original move.
3. Hide or remove the original move from the exercise branch.
4. Ask the user to choose a move.
5. Analyze the user's choice.
6. Compare it with the original move and best candidate(s).
7. Explain the difference.
8. Show a verified continuation.
9. Record the result as a training attempt.

Acceptance criteria:
- Original game data is never overwritten.
- The user can retry a position.
- The move comparison uses the same starting FEN and compatible analysis settings.
- Exercise results are stored separately from original game moves.

24. LLM PROMPT AND RESPONSE SAFETY CONTRACT
======================================================================

Every chess-coaching request should provide the model with a bounded, structured context rather than expecting it to remember the game from chat history.

Provide relevant fields such as:
- Current FEN
- Side to move
- Last move
- Actual game move
- Legal moves when needed
- Engine candidate moves
- Evaluation with explicit perspective
- Principal variation
- Relevant material/position features
- Detected motifs and confidence
- The coaching question and desired explanation level

The model must:
- Use only supplied engine values as engine facts.
- Not invent a legal line.
- Not invent a score or claim a move was engine-best without evidence.
- Clearly distinguish the actual game from a hypothetical variation.
- Return a defined response schema for visual actions.
- Mark uncertain interpretations as uncertain.
- Never directly mutate board state.
- Never bypass the server's move validator.

If the model returns a move or line, parse and validate it against the appropriate position before displaying it as a verified line or animating it.
